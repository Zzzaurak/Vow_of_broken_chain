# 《断链之誓》开发 Plan（修订版）

本计划依据 [企划 v0.5](../material/AI娘冒险游戏_简版企划书.md)、[完整剧本](../material/script.md)、[Scala 课程规范](../../course-skills/scala-course-homework/SKILL.md) 与 [React 课程规范](../../course-skills/react-course-frontend/SKILL.md)。用于指导后续实现和验收，不代表以下工作已经完成；实际工程状态另见 implementation-status.md。

## 1. 服务边界与技术方案

采用 React + TypeScript + Tailwind + Canvas 2D、Scala 3 + Cats Effect + http4s + Circe、PostgreSQL。浏览器承担即时模拟，后端承担可信玩家身份、冒险与存档持久化。采用课程允许的逻辑服务划分，同一后端进程部署，不额外搭建网关、服务发现、消息队列或每服务独立数据库。

**保留两个业务服务，另有 system 基础设施模块。** 服务按独立业务责任划分，不按游戏里出现的名词划分。

| 模块 | 职责与所属表 | 公开／内部 API | 调用关系 |
| --- | --- | --- | --- |
| PlayerService | 匿名玩家、访问令牌、可信身份；PlayerTable、PlayerSessionTable；玩家进度版本及继续指针归玩家记录维护 | 公开 CreateAnonymousPlayerMessage；内部 ResolvePlayerMessage | 路由调用身份解析；Adventure 消息调用公开玩家表方法更新进度版本／继续指针 |
| AdventureService | 新冒险、难度、快照校验、手动／自动存档、回档与请求去重；AdventureTable、GameSaveTable、ProgressOperationTable | 公开 StartAdventureMessage、ListSavesMessage、LoadAdventureMessage、SaveProgressMessage；内容校验为服务内函数 | 消息 plan 组合校验及公开 Table 操作，共用事务连接 |
| system | 服务器启动、连接与事务、APIMessage、通用路由、错误响应 | 基础设施接口，不作为第三个业务服务 | 两服务共同使用；不存放游戏业务 SQL |

**玩家与可操作角色是两种概念。** 玩家是存档所有者；DeepSeek、伙伴和 NPC 是内容定义及冒险状态。角色解锁、援助配置属于冒险快照，不需要 CharacterService。

这里的“两服务”指课程中的两个逻辑业务边界，不是两个独立部署的分布式微服务。服务数量不作为代码质量目标；代码质量通过职责清晰、类型与状态正确、事务可靠、契约一致和可验证行为体现。按课程 Scala 技能的“规划与后续确认”及规则 1–12 组织，不为增加数量拆出只有转发功能的服务。

| 游戏概念 | 独立模型／模块 | 数据归属与是否单独建服务 |
| --- | --- | --- |
| 玩家 | PlayerId、玩家记录、会话 | PlayerService；真实身份与存档所有权边界 |
| 主角、伙伴、NPC | CharacterDefinition、解锁与援助配置 | 定义在 characters 内容；本次冒险状态由 AdventureService 保存，不另建角色服务 |
| 地图 | MapDefinition、碰撞与导航函数 | 定义在 world 内容；当前位置进入冒险快照，不另建地图服务 |
| 关卡／遭遇 | EncounterDefinition、波次、触发与胜利状态机 | 定义在 encounters 内容；完成标记进入冒险快照，不另建关卡服务 |
| 敌人 | EnemyDefinition、EnemyInstance、行为与伤害计算 | 基础定义归内容配置，战斗实例归浏览器运行态，不为每只敌人建表或接口 |
| 剧情与任务 | StoryNode、推进条件、阶段标记 | 定义在 story 内容；进度由 AdventureService 校验并保存 |

上述模型名表示规划职责，具体文件名随现有工程统一。静态定义与玩家进度分开：前后端从同一份版本化内容生成各自需要的产物，避免两套手工维护的数值。静态内容首版随应用发布，不为只读配置强行建立 CRUD 服务；后端仍承担身份、所有权、存档校验及事务这些实际业务。

地图、敌人、关卡使用版本化内容配置：地图定义地形与碰撞，遭遇定义刷怪与胜利条件，敌人定义行为与数值，角色定义素材与技能。运行时实例由前端纯函数更新；后端使用相同内容版本验证安全快照。无需为每次移动、攻击、刷怪调用网络，也不声称提供服务端权威反作弊。

未来只有出现独立的内容编辑与发布、多人权威战斗、跨冒险角色养成等明确业务时，再评估 ContentService、BattleService 或 CharacterService；当前不预建空服务。

### 两个服务之内如何保持模块清晰

不独立部署，不代表把角色、地图、敌人逻辑都塞进一个文件。按下表确定代码职责；目录是拟定的业务归属，已有实现满足边界时沿用，不为目录名称重写代码。

| 模块 | 输入与输出 | 实现边界 |
| --- | --- | --- |
| 角色与技能 | 角色定义、解锁、援助槽、操作 → 行动与资源变化 | content/characters 保存定义；GamePage 的 objects 与纯计算负责实例及技能；AdventureService 校验已解锁角色和可保存配置 |
| 地图与碰撞 | 地图定义、当前位置、移动量 → 合法位置与交互候选 | content/world 保存布局；GamePage 的纯函数处理移动、碰撞与出口；绘制层仅消费结果 |
| 遭遇与流程 | 遭遇定义、剧情阶段、存活敌人 → 当前波次、胜负及下一阶段 | content/encounters 保存编排；GamePage 的流程函数推进；AdventureService 校验保存阶段与完成标记的一致性 |
| 敌人行为 | 敌人定义、玩家位置、行动阶段、时间步 → 下一敌人状态与攻击事件 | 内容定义与运行实例分离；GamePage 的纯计算实现近战、远程、盾卫和各 Boss 状态机，不在渲染代码中扣血 |
| 存档 | 安全快照、可信玩家、预期版本、操作 ID → 已提交快照或明确错误 | AdventureService 的消息组合校验与公开 Table 操作；PlayerService 维护身份及玩家级版本；数据库提交后前端才确认成功 |

一次“清场后保存”的调用链：GamePage 纯计算得到清场状态 → SaveProgressMessage.send() → 路由解析可信 PlayerId → 后端 SaveProgressMessage.plan(connection) → 同一事务校验内容与版本、写入存档并更新玩家继续指针。角色、地图和敌人的数据都参与流程，但不需要三次额外网络调用。

将来拆服务的条件必须是新增业务责任：内容编辑／审核／发布可形成 ContentService；跨冒险的角色培养与资产可形成 CharacterService；多人实时权威战斗可形成 BattleService。真正独立部署时还需重新设计事务和调用契约，不能把当前共享连接的 Table 调用直接搬到网络两端。当前课程首版不承担这些分布式复杂度。


后续功能修订将注册、登录、退出和账号表归入 PlayerService。游客注册沿用原玩家 ID，登录签发独立会话。账号页位于 `/account`，最新 API 对照、启动器控制和全屏操作见[项目 README](../README.md)。

## 2. 页面与跨端契约

| 页面目录／URL | 用途、主要区域 | 依赖 |
| --- | --- | --- |
| frontend/src/pages/StartPage，`/` | 标题、新冒险、难度、继续、选档、设置 | PlayerService、AdventureService |
| frontend/src/pages/GamePage，`/game` | Canvas、HUD、立绘对白、援助配置、暂停、存读档、失败重试、CG 与结局 | AdventureService；复用已建立的玩家身份 |

设置与存档列表按复用需要抽取，共享不等于新增页面。以下目录为目标组织，按实际复杂度创建，不为对称增加空目录：

```text
frontend/src/
  api/                         # 公共传输、稳定消息名、令牌与错误
  apis/PlayerService/          # 与后端同名的请求类
  apis/AdventureService/
  pages/StartPage/
  pages/GamePage/
    components/ hooks/ objects/ functions/ runtime/
  features/settings/           # 跨页偏好
  features/audio/              # 音频副作用边界
backend/src/main/scala/services/
  PlayerService/                # api、objects、routes、tables、utils 按需
  AdventureService/
  system/                      # database 为基础设施目录例外
content/
  characters/ world/ encounters/ story/ balance/
```

| 页面操作 | 前端请求类 → 同名后端消息 | Table／计算 |
| --- | --- | --- |
| 首次访问 | CreateAnonymousPlayerMessage | 生成令牌并保存摘要 → PlayerTable、PlayerSessionTable |
| 新建冒险 | StartAdventureMessage | 初始内容／难度 → AdventureTable、GameSaveTable、PlayerTable、ProgressOperationTable |
| 查看存档 | ListSavesMessage | 可信玩家归属 → AdventureTable、GameSaveTable、PlayerTable |
| 读取／继续 | LoadAdventureMessage | 归属、版本及快照校验 → GameSaveTable、PlayerTable、ProgressOperationTable |
| 手动／自动保存 | SaveProgressMessage | 安全状态校验、版本及幂等检查 → AdventureTable、GameSaveTable、PlayerTable、ProgressOperationTable |

请求类构造仅保存 readonly 输入，send 才请求；稳定消息标识统一推导路由，显式序列化字段，不使用 constructor.name。路由将令牌解析成可信 PlayerId，不信任客户端自报身份。内部 ResolvePlayerMessage 不公开为 HTTP 接口，不要求前端调用器。

## 3. 地图与关卡设计

由开发阶段完成布局、碰撞、敌人位置、预警和环境细节设计；不改写作者剧情顺序。首版采用 12 个紧凑房间、5 组环境素材、8 个战斗节点。地图尺寸以可读、可走位为准，不扩大成开放世界。

| 房间 ID／地点 | 布局与体验 | 遭遇／推进条件 | 安全点 |
| --- | --- | --- | --- |
| steps 长阶 | 阶梯形成纵向引导，平台提供横向避伤空间 | 0-A：3 名近卫，教学后才进入强制分离 | 教学战前 |
| market 东方集市 | 摊位围出清楚主路，Qwen 与出口形成视觉引导 | 指路对白，无战斗 | 出发补给 |
| forest 林道 | 曲折主路配两处宽阔战斗空地，树木不封死退路 | 1-A：3 晶石兽＋2 术士 | 入口／清场后 |
| harbor 迷雾港镇 | 货箱、码头及可绕行小环路，追逐后进入开阔场地 | 2-A：GLM 事件战，低于最大 HP 的 30% 投降 | 事件战前；结束后解锁 GLM |
| coast 西海岸 | 岸线、穹顶远景与路标，渡海落点不刷怪 | 结界受阻与线索对白 | 登陆点 |
| crystal 晶石林 | 晶簇隔断视线但保留侧路，控制技能有使用空间 | 3-A：4 机械猎犬，救援 Gemini | 战前／取得星图后 |
| pass 北境山道 | 折返登山路径、雪景与龙巢轮廓，不加坠落判定 | 旅行衔接，无新增必打战 | 龙巢入口 |
| lair 龙巢 | 大型开阔竞技场，龙息方向与星落范围明确 | 4-A：GPT 独立护盾破碎后，实际伤及本体一次即成功 | 试炼前；治疗休整后 |
| corridor 教堂回廊 | 柱列提供路线选择，刷怪点远离玩家出生点 | 5-A：3 波守卫，清完一波才刷下一波 | 回廊战前／结束后 |
| garden 圣女内庭 | 中央向日葵庭院、环绕走位区，花阵与装饰区分 | 5-B：仅破 Claude 护盾，不伤本体；指定阶段暂停呼唤 | 切磋前／Claude 入队后 |
| throne 主殿 | 中央战场、明确安全扇区，边界不藏预警 | 5-C：D 教皇双阶段，半血转阶段，结界净化提供反击窗口 | 终战前独立准备点 |
| alley 自由小巷 | 复用街道，增加两碗白米饭及重逢摆位 | cg1 → cg2 后日谈 → 制作名单与完成记录 | 保存最终完成状态 |

回廊按企划的“持盾骑士 → 术士 → 混合队”编排，初始数量建议为：第一波 2 持盾骑士；第二波 3 术士；第三波 2 持盾骑士＋2 术士。数量经试玩调整，原剧本明确指定的数量优先，不用困难模式增加波次或人数。

每张地图需定义稳定 ID、版本、尺寸、图层、碰撞体、出生点、出口、交互区、安全点、遭遇引用、剧情触发与解锁条件。构建检查引用存在、出生／保存位置合法、出口可达；试玩检查敌人绕障、预警可见、镜头不遮挡、没有无法结束的遭遇。普通敌人必要时使用简单网格寻路，支援角色无需跟随寻路。

地图、关卡和小怪的细化设计由开发过程完成，无需作者另交布局稿。每关按以下顺序交付：

1. 灰盒布局：标出出生点、主路、绕行区、障碍、出口与镜头范围，先验证可达性。
2. 遭遇配置：明确怪物种类、数量、位置、波次、触发／结束条件及失败重试点；普通攻击应始终能完成必要战斗。
3. 内容接线：接入剧本节点、伙伴解锁、自动存档边界，确保退出重进不会重复领取或跳过剧情。
4. 视觉与反馈：补齐环境图层、敌人素材、前摇、命中与死亡表现，装饰不伪装成攻击预警。
5. 双难度试玩：真实操作检查走位空间、出生安全、清场和重试；记录需调整的数值及通过证据。

先完成长阶教学与林道混合敌人的代表性关卡，再将验证过的结构扩展到其余地图；每关都必须通过上述出口条件，不能仅以配置文件存在判定完成。

每关保留一份可审查的设计记录：地图尺寸与出生／出口坐标、障碍布局、刷怪点、波次、敌人基础参数、预警时长、通关条件、重试点，以及对应的测试或试玩结果。具体坐标与数值由开发时设计并集中配置；先证明可达、可躲、可完成，再调整画面和节奏。不能把敌人伤害、碰撞尺寸或刷怪位置分散成组件中的魔法数字。

关卡验收至少覆盖：未完成遭遇时不能跳关；清场后出口可达；敌人不会刷进障碍或安全出生区；远程敌人能被接近，近战敌人不会永久卡住；所有必经战斗无需尚未解锁的伙伴；失败重试恢复本关初始状态；保存并刷新后不会重复触发奖励或退回未清场状态。Boss 还须逐一验证下节列出的特殊胜利条件。


### 林道 1-A 的实现与验收样例

用林道作为地图、敌人、关卡与两项后端服务的联合验收关。每个模块交付一项可观察的行为，后续关卡沿用这套分工。

| 玩家操作 | 设计与实现归属 | 验收观察 |
| --- | --- | --- |
| 从集市进入林道 | 地图配置入口、树木碰撞、两块可走位空地与出口。剧情节点决定能否推进 | 玩家从安全位置入场，能绕树抵达战斗区；提前走到出口不会跳过遭遇 |
| 进入战斗区 | 遭遇配置引用 3 只晶石兽和 2 名术士。晶石兽从前方逼近，术士从侧面施压，给玩家留出横向脱离路线 | 近战前摇与远程预警可辨认；玩家能绕开第一轮攻击，仅用基础攻击也能清场 |
| 清场后手动存档 | 战斗逻辑产出清场状态。PlayerService 解析玩家身份，AdventureService 校验安全阶段并在同一事务中写入快照与继续指针 | 保存成功后刷新并继续，回到已清场的林道，位置、资源与伙伴配置恢复，出口可用 |
| 以困难难度重玩 | 同一遭遇读取难度规则，按基准计算敌人生命与伤害 | 仍出现 3 只晶石兽和 2 名术士，生命及伤害为简单模式的两倍；走位路线与攻击预警时长一致 |

## 4. 小怪与 Boss 设计

三类普通行为搭配不同外观，避免每种外观都复制一套 AI。数值集中配置，首轮通过教学与代表性遭遇试玩确定简单模式基准。

| 行为 | 外观 | 攻击节奏与玩家应对 |
| --- | --- | --- |
| 追击近战 | 近卫、晶石兽、机械猎犬 | 接近 → 可见前摇 → 有限范围打击／短扑 → 收招；通过走位、GLM 束缚和水球范围攻击应对；不同外观允许配置不同基础速度，但两难度不改变速度 |
| 远程施法 | 教会术士 | 保持距离 → 标记落点或弹道 → 施法 → 冷却；可躲避，不在玩家脚下无预警生效 |
| 正面防御 | 持盾骑士 | 正面防御 → 缓慢接近 → 有前摇攻击；绕背或 GPT 星落短暂破防，不设计必须有某角色才能清场的死锁 |

Boss 使用独立状态机：GLM 移动／符文闪避／书页炸弹；GPT 星落与冰极龙息；Claude 防御护盾与减速花阵；教皇第一阶段基础攻击、第二阶段禁锢法阵。具体判定优先于动画，动作 ID 保证单次伤害结算。

硬性数值与胜利约束：

- 玩家 HP／MP 上限始终 100；水球当前基准消耗 20 MP、CD 4 秒、MP 回复每秒 2；援助 CD 为 GLM 10、GPT 18、Claude 16 秒，调整须同步企划与测试。
- 困难仅使敌态最大 HP／初始 HP 和伤害乘 2；独立护盾、敌人数、速度、前摇、CD、支援能力均不加倍。
- GLM 低于相对 30% HP 投降；GPT 破盾并受一次实际本体伤害即胜利，同帧胜利优先于普通死亡；Claude 只破盾；教皇相对 50% HP 转阶段。
- 剧情重伤是过场状态，不能产生失败菜单或濒死存档；终战前独立检查点，失败不要求重打 Claude。

## 5. 状态、存档与课程代码要求

即时游戏状态与可保存快照分离：战斗运行态包含敌人、弹体、行动阶段；安全快照保存冒险／内容版本、难度、地图和位置、剧情阶段、任务、伙伴、援助槽、HP／MP 与 CD。战斗和连续过场中不开放保存。

每次冒险保留 5 个手动槽与最近 3 条自动记录。覆盖前确认；数据库事务完成后才显示成功；新冒险不删除旧记录。回档忠实恢复资源与 CD，检查点重试恢复资源并重置遭遇，两者分别建模。设置独立保存在浏览器，不随剧情回档。

保存／载入使用操作 ID、请求去重、玩家进度版本与事务；载入增加版本，拒绝旧分支请求。前端隔离旧响应，重试复用原操作 ID，载入不立即触发自动保存。覆盖、网络失败、并发、多标签页冲突和不兼容内容版本均需有明确反馈。

课程规范落实为阶段审查项：

- Scala 业务数据 final case class、同文件伴生编解码器、每个领域对象独立文件；有限状态采用 enum／封闭类型。
- 消息 plan(connection): IO[A] 清楚组合业务步骤；副作用在 IO／Resource，业务不使用 var、命令式循环、Try、try/catch 或 unsafeRun。
- Table 公开方法返回 IO，封装 SQL、参数及行映射；SQL 私有，utils 限服务内；跨服务允许调用公开 API 和 Table，不增纯转发层。
- React 页面逻辑就近放置；纯函数从输入推导展示，避免重复状态；Zustand store 私有，通过订阅／快照／更新函数访问。
- 使用 Tailwind；Canvas 绘制属于游戏画面边界。两套独立改键覆盖战斗、对白和菜单，冲突交换／取消，失焦清键并暂停。
- README 同步真实 services、pages、公开 API、目录例外及运行方法；编译通过不能替代课程规范审查。

## 7. 验证与范围控制

纯函数测试覆盖技能扣费、冷却、碰撞、每次攻击只结算一次、难度倍率、Boss 阈值与剧情状态转移。真实 PostgreSQL 集成测试覆盖归属、5＋3 槽、事务回滚、幂等和回档版本。浏览器通过真实输入验证完整流程、纯键盘菜单、设置持久化和保存／载入竞态；模拟直接清敌的测试只能证明状态衔接，不能代替通关试玩。

保留原立绘与 CG，缺失地图、敌人和特效按清单设计制作，记录来源、图集分格和锚点。公开发布前按实际素材许可处理。后续修订已在 PlayerService 中增加账号注册和登录，保留游客直接开始冒险。首版不增加多人联机、角色养成、商店、装备、开放世界或实时 AI 剧情；这些不是完善前后端课程项目的必要条件。
